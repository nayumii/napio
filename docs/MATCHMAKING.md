# Factorio matchmaking: what the protocol actually is, and why napio does not use it yet

> **Status: implemented, verified end to end with a real Factorio client, and
> off by default.** A sleeping server published by napio was found in the real
> public server browser, and clicking Join woke it and let the player in — see
> [what was verified](#what-was-verified).

Captured from **Factorio 2.0.77, build 84539, headless, linux64** on 2026-08-29,
and verified end to end against **Factorio 2.1.17, build 87315** the same day.
Everything here is observed traffic, not documentation — Wube documents none of
this, and both the [wiki](https://wiki.factorio.com/Matchmaking_API) and the
[community API docs](https://artentus.github.io/FactorioApiDoc/matchmaking-api/)
mark these endpoints "TODO".

---

## The goal

A sleeping server is not in the public server browser, because the listing is a
heartbeat published by the running Factorio process (see
[ARCHITECTURE.md §10](ARCHITECTURE.md#10-limitations-imposed-by-factorio-itself)).
If napio could publish that listing itself while the server sleeps, a player
could find a sleeping server in the browser and wake it by clicking Join.

That requires knowing exactly what a Factorio server sends to
`multiplayer.factorio.com`. Now we do.

## How it was captured

Factorio validates TLS against a bundled CA (`/opt/factorio/data/cacert.pem`)
and the system store, so a lab CA is added to both, and
`multiplayer.factorio.com` is pointed at a local HTTPS server with `--add-host`.
`auth.factorio.com` is proxied through to the real service, because the server
refuses to start a public game without a genuine padlock.

Full rig, including the one-command run: [`hack/matchmaking-lab/`](../hack/matchmaking-lab).

## The protocol

A public dedicated server performs this sequence at startup:

```
1. POST https://auth.factorio.com/generate-server-padlock-2?api_version=6
2. GET  https://auth.factorio.com/tls-check/success
3. POST https://multiplayer.factorio.com/create-game
4. POST https://multiplayer.factorio.com/post-game-heartbeat/{game_id}   every 30 s
5. POST https://multiplayer.factorio.com/remove-game/{game_id}           on clean exit
```

All requests are `Content-Type: application/json` with
`User-Agent: Factorio/2.0.77 (build 84539, linux64, headless; Linux)`.

### 1. Server padlock

```http
POST https://auth.factorio.com/generate-server-padlock-2?api_version=6
(no body, no credentials)
```

```json
{"server_hash": "9k7C66LDMWCyY5X6FdvPOK3WXnjXH1r4",
 "server_padlock": "2smEY/7RNEsuI2RDFIP8hmSobQyRx..."}
```

Unauthenticated — anyone can call it. The server logs
`Obtained serverPadlock for serverHash (...)`. Omitting either field makes the
server fail with `Response from the auth server is missing the server_padlock.`
and exit; this step is mandatory because `require_user_verification` must be
enabled for public games.

### 2. TLS check

`GET https://auth.factorio.com/tls-check/success` → the literal body `OK`.

### 3. Create game

```http
POST https://multiplayer.factorio.com/create-game
```

```json
{
  "game": {
    "game_id": 4294967295,
    "game_secret": "xI2JDKeqFTywTVErFSfeOHEUJQvcKuXe",
    "name": "napio lab server",
    "description": "protocol capture lab",
    "tags": ["napio", "lab"],
    "application_version": {
      "game_version": "2.0.77",
      "build_version": 84539,
      "build_mode": "headless",
      "platform": "linux64"
    },
    "max_players": 8,
    "game_time_elapsed": 0,
    "has_password": false,
    "host_address": "<public-ip>:34197",
    "host_port": 34197,
    "mods": [
      {"name": "base", "version": "2.0.77"},
      {"name": "elevated-rails", "version": "2.0.77"},
      {"name": "quality", "version": "2.0.77"},
      {"name": "space-age", "version": "2.0.77"}
    ],
    "headless_server": true
  },
  "username": "napio-lab-user",
  "token": "0123456789abcdef0123456789abcd"
}
```

Response from the lab: `{"game_id": 4242, "game_secret": "..."}`, after which the
server logs `Matching server game '4242' has been created.` The **live** service
answers `{"game_id": …, "server_id": "…", "server_secret": "…"}` — no
`game_secret` at all, which is consistent with the next point.

Three non-obvious properties, each verified rather than assumed:

- **`game_id: 4294967295`** (`0xFFFFFFFF`) is the "no id yet" sentinel in the
  request. The real id comes back in the response.
- **`game_secret` is generated by the server, not the service.** The lab
  responded with a *different* secret and the server ignored it, continuing to
  use its own in every later request. The secret is the server's proof that it
  owns the listing.
- **`host_address` is what the server learned from the pingpong servers**
  (`pingpong1..4.factorio.com:34197`, UDP), not from the HTTP connection. The
  server asks them "what is my address" before registering.

### 4. Heartbeat

```http
POST https://multiplayer.factorio.com/post-game-heartbeat/4242
```

```json
{"game_secret": "xI2JDKeqFTywTVErFSfeOHEUJQvcKuXe",
 "game_patch": {"game_time_elapsed": 0}}
```

**Every 30 seconds**, measured over 14 consecutive heartbeats (gaps: 30.0 s,
with one 59.8 s gap where a beat was skipped). The body is a **patch**, not a
full state: only fields that changed since the last heartbeat are sent. On an
empty, auto-paused server the patch stays `{"game_time_elapsed": 0}` because the
tick does not advance.

### 5. Remove game

```http
POST https://multiplayer.factorio.com/remove-game/4242
{"game_secret": "xI2JDKeqFTywTVErFSfeOHEUJQvcKuXe"}
```

Sent during a clean shutdown, immediately before `Goodbye`. A server that is
killed never sends it, so the service must also expire listings on missed
heartbeats — the expiry window was not measured (it needs the real service).

## What was verified, and what was not

The protocol above was captured from a lab. Everything below was then run
against the **real** `multiplayer.factorio.com` with a real account token, with
Factorio stopped and napio holding the UDP port.

| Question | Answer | How it was established |
|---|---|---|
| Does the service accept a listing published by something that is not a running Factorio server? | **Yes.** `create-game` returned `{"game_id":…,"server_id":…,"server_secret":…}` and the listing appeared in `get-games` alongside 3 189 real servers. | Published from napio with Factorio stopped. |
| Does the service UDP-probe the advertised address before publishing? | **No.** napio held the port for the whole window and received **zero** datagrams. | napio logs every datagram at debug level. |
| Does the listing survive heartbeats? | **Yes.** `last_heartbeat` advanced every 30 s. | Observed over multiple beats via `get-game-details`. |
| Is the client-facing metadata correct? | **Yes.** `get-game-details` returned the name, description, tags, `max_players`, mod list and exact build napio advertised. | Compared field by field. |
| Can `game_time_elapsed` be omitted? | **Yes.** The service accepts a listing without it, so napio never invents one. | Published without the field. |
| Does `remove-game` work? | **Yes.** `get-game-details` returns `{"message":"no game for given game_id"}` afterwards. | On wake, on shutdown, and on napio exit. |
| What does a bad token do? | `HTTP 401 {"message":"Token doesn't match."}`. napio treats it as fatal, disables the listing and keeps working as a gateway. | Ran napio with a deliberately wrong token. |
| **Does clicking Join in the real client's public browser reach napio?** | **Yes.** The connection requests arrive at the advertised address, the wake fires and the player joins. | Factorio 2.1.17 client, listing found by name in Browse public games, Join clicked. |

### The end-to-end run

Factorio 2.1.17 client, Factorio 2.1.17 headless server stopped, napio holding
the port and advertising the listing:

```
17:59:59.485  listing published                    game_id=1311176
18:00:16.213  datagram received  bytes=3           wakes_server=false
18:00:16.238  datagram received  bytes=3           wakes_server=false
18:00:16.738  datagram received  bytes=3           wakes_server=false
18:00:17.043  datagram received  bytes=14          wakes_server=false
18:00:17.558  datagram received  bytes=14          wakes_server=true
18:00:17.558  connection attempt detected
18:00:17.585  withdrew the public listing                       (27 ms)
18:00:17.585  starting server
18:00:18.773  server is online                                  (1.2 s)
18:00:29.223  inactivity countdown cancelled       players=1
```

Join to playing: **about 13 seconds, on the first attempt.** The client's own
retry window covered the whole start, so the player never saw a timeout. That
is the good case — a container with a large save, or a cold start, will still
exceed the client's ~10 s patience and need a second attempt.

Two things in that trace are worth keeping:

- **The client sends 3-byte datagrams before the real connection requests.**
  They arrive as soon as a player looks at the server, and the default
  `wake.min_packet_size: 4` filters them out. Without that floor, simply
  *browsing* the public list would wake every sleeping server it contains.
- **The connection request is 14 bytes and is retried**, which is exactly the
  behaviour the wake filter is built on: the second one fires the wake, half a
  second after the first.

The feature nevertheless remains off by default, because publishing a listing
is a deliberate act that requires an account token and a public address.

### Accuracy

A listing that is wrong is worse than no listing. Every advertised field is
traceable to a real source:

| Field | Source |
|---|---|
| `name`, `description`, `tags`, `max_players`, `has_password`, `username`, `token` | `server-settings.json` — the same file Factorio reads |
| `mods` | `mods/mod-list.json` plus the versions in the mod archive filenames; base and DLC carry the game version, exactly as a real server sends |
| `application_version` | the `Factorio 2.0.77 (build 84539, linux64, headless…)` banner in the server's own log, read through the backend |
| `host_address`, `host_port` | `matchmaking.public_address`, which napio refuses to guess |
| `game_time_elapsed` | **not sent** — napio cannot observe the tick count while the server is off, and will not invent one |

If any of those cannot be read, napio publishes nothing and says why. It never
falls back to a default. In particular, a server whose version banner napio has
never seen is not advertised: start it once and the banner is picked up from the
backend's log.

The description carries a note — `[napio: asleep - joining wakes it, retry in
~30s]` by default, configurable — so players in the browser know before they
click that the first attempt wakes the server and the second one joins.

## Reproducing the verification

> **Be brief.** A listing that points at a server nobody can join pollutes the
> public browser for real players. napio removes its listing when the server
> wakes, when it stops and when napio exits — but keep deliberate tests short.

1. Configure `matchmaking` for a server reachable at the address you advertise
   (see [CONFIGURATION.md](CONFIGURATION.md#matchmaking)).
2. Start napio with Factorio stopped. Confirm `state: offline`,
   `listener_bound: true` and `listing.listed: true` in the API.
3. Open Factorio → Multiplayer → Browse public games and find the server.
4. Click **Join**.
5. With `log_level: debug`, napio logs every datagram it receives, so the whole
   chain is visible: `datagram received` → `connection attempt detected` →
   `withdrew the public listing` → `server is online`.

**The advertised address has to be reachable from the client.** Two traps cost
an hour during the original verification, both of them local network problems
rather than napio ones:

- **NAT hairpin.** A client on the same LAN as the server cannot usually reach
  its own WAN address; most consumer routers do not loop UDP back. Test from
  outside the network, or advertise the LAN address while testing locally.
- **Host firewalls do not treat napio and Docker alike.** Docker publishes
  ports by inserting its own DNAT and FORWARD rules, which bypass `ufw`
  entirely, so a *running* Factorio container is reachable while a *sleeping*
  napio — an ordinary host process subject to the `INPUT` chain — is not. The
  symptom is a server that is listed but unreachable only while asleep. Fix:
  `sudo ufw allow 34197/udp`.

There is also an opt-in test that exercises the whole listing lifecycle against
the live service:

```console
$ NAPIO_INTEGRATION_FACTORIO_TOKEN=... \
  NAPIO_INTEGRATION_FACTORIO_USERNAME=... \
  NAPIO_INTEGRATION_PUBLIC_ADDRESS=203.0.113.7:34197 \
  go test ./internal/integration/ -run RealService -v
```

## Compatibility note

Everything here is undocumented and unversioned. It was true for 2.0.77 on
2026-08-29 and Wube is free to change it without notice.

napio therefore treats the listing as strictly optional. Every failure path is
non-fatal and was tested: an unreachable service retries with backoff (30 s
doubling to 10 minutes) while the gateway keeps waking servers normally; a
rejected token disables the listing and logs it once rather than hammering the
service; a failed heartbeat republishes rather than leaving a listing to rot.
napio heartbeats at the same 30-second cadence as a real server and never
faster.

If a future Factorio version changes the protocol, re-run
`hack/matchmaking-lab/run.sh` and update this document.
